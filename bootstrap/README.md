# Bootstrap

This directory holds the compiled compiler. `nio.ll` is `src/nio.nio` as
portable LLVM IR. `build.sh` turns it into a working `nio` on a machine that
has only clang.

```sh
sh bootstrap/build.sh          # writes ./nio
./nio build --release src/nio.nio -o nio # ...and from here it builds itself
```

Both files are generated by `nio run tools/bootstrap.nio`. Do not edit either
of them by hand.

## Why a checked-in artifact

The compiler is written in the language it compiles, so building it needs a
compiler. Something has to break that circle, and `bootstrap/nio.ll` is stage 0.

The artifact is IR, not prebuilt binaries, for two reasons. It adds no
dependency beyond clang. It is also text that a reviewer can read and diff,
which matters for a bootstrap compiler. It has no `target-cpu`, no
`target-features`, no triple and no datalayout, so clang lowers it for the host
that runs it. It assumes a 64-bit host, through `types.naturalBits`.

## The rule

**Regenerate whenever `src/` changes.** Do not wait for a release. An artifact
that lags cannot build the tree it is checked in beside, and nothing warns you
before it fails. For example, `src/lib/fmt.nio` indexes a `String`. A stage 0
from before that feature rejects it, and the repository has no other way to
build the compiler.

`tests/bootstrap_test.nio` asserts one equation:

    bootstrap/nio.ll == the IR the compiler in src/ emits for src/nio.nio

The checked-in text is therefore the current compiler, and any drift is a
failing test. `tests/fixpoint_test.nio` checks the other half. Clang builds
`nio0` from the IR here, `nio0` builds `nio1`, and `nio1` builds `nio2`.
`nio1` and `nio2` must be byte-identical. `nio0` is not compared: the IR
carries no target attributes, so `nio0` is always a different file. What must
match is the compiler that `nio0` builds.

## Using a new language feature inside the compiler

The equation makes this cost two commits. This is the one change that can
leave the repository unable to build itself, and the test refuses it in the
same commit instead of a month later.

1. **Teach the compiler the feature**, without using it in `src/`. Regenerate.
   The checked-in IR now implements the feature.
2. **Use it.** Regenerate. Stage 0 from step 1 understands it.

You can do both at once and still pass the equation, if you regenerate through
an intermediate compiler that you build locally. But then no commit in history
can produce the artifact, and a reviewer can verify the fixpoint but cannot
reproduce it. With two commits, each commit can be built by the compiler of the
commit before it. This makes walk-forward recovery possible if an artifact is
ever too old: build the newest commit it accepts, then step forward one commit
at a time.

A script checks this, because the equation does not. At `HEAD` everything is
self-consistent either way. What is lost is a property of the commit range.
`tools/walkforward.sh` builds each recent commit with the compiler of the
commit before it, and fails with the name of any commit that cannot be built.
`.github/workflows/walkforward.yml` runs it weekly. Run it by hand over the
range you are about to push:

```sh
sh tools/walkforward.sh 20
```

## If everything is broken

Use walk-forward recovery: find the newest commit that a working stage 0 can
build, then step forward one commit at a time.

The recovery path is walk-forward from `bootstrap/nio.ll`.
